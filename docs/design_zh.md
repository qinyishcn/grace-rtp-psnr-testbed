# GRACE 特征块传输及网络侧 PSNR 预测设计

目标链条是“信源 → 真实 GRACE 特征 → 十个独立编码块 → RTP 分片 → 受扰动网络 → 截止时间重组 → 部分特征解码 → 帧级 RGB PSNR → 网络侧预测”。帧级标签必须来自实际收到的字节和独立接收参考帧。

## 核心判断

两段分解有物理意义：网络决定哪些块能在截止前完整交付，应用决定这些块以及参考帧状态如何影响重建失真。不过第二段不是单一的“丢块率 → PSNR”函数。相同丢块率下，运动、残差内容、具体掩码、质量档、GOP 位置及先前失真均能改变结果。第一段的概率输出也不应阈值化后当作确定真值。应传播分布或多次采样，预测均值和区间。

仅在上游抓包不能辨识下游接收结果：同一段上游抓包可以对应完整交付或下游全部丢失。若要预测实际丢块，必须说明观测位置，并提供接收侧抓包、RTCP/块状态反馈，或网络中可观测的排队/丢弃事件。本实现将“上游抓包”与“同步的收发两处抓包”分别评估；后者的延迟统计需要同步时钟。使用 SI/TI 的实验独立标为信源反馈增强，不能称为纯被动抓包。

在默认 SRTP 下，RTP 基本头中的序列号、时间戳和 SSRC 可见，而自定义载荷头受到加密保护。实验中的块头在载荷内，接收端能解密解析，旁路网络节点不能读取。可部署方案是经过协商的明文 RTP 扩展（需同时考虑扩展加密），或单独发送可见、受认证的块布局/状态反馈。CRC 仅用于实验中的整块完整性校验，不能替代 SRTP 的认证。[SRTP](https://www.rfc-editor.org/rfc/rfc3711.html)、[扩展加密](https://www.rfc-editor.org/rfc/rfc6904.html)。

## 为什么按十块，而不是按 IP 包或张量元素丢失

先把 motion 与 residual 拼接符号按索引 `b::10` 交织成十块；每块独立 DEFLATE 压缩并携带完整块 CRC；再分成 RTP 包。包头含版本、frame_id、block_id、fragment_id、fragment_count、block_crc32。一个 IP/UDP 数据报承载一个 RTP 分片，MTU 限制用于避免 IP 分片。本实验 RTP 上限 1200 字节，IPv4/UDP 再加 28 字节，SRTP 还需加认证标签等开销。

接收端必须收到块的所有唯一分片且 CRC 正确，才能解压；其他块完整保留，坏块恢复为零。可靠布局元数据必须包含预期帧号与时序，才能处理整帧一个包都没收到的情况；不能依靠 marker 到达才知道有一帧。

对于一个有 n 个包的块，独立有效丢包概率为 p 时，块丢失概率是 `1-(1-p)^n`。例如 p=1%、n=10 时为 9.56%；n=50 时为 39.50%。不能把配置包丢失率直接当作特征损失率。不同块压缩长度不同，实际 n 也不同；突发丢失时独立公式失效，包的发送顺序和块间交织会进一步影响掩码。

十块是可控的原型选择，不保证最优。应后续比较 5/10/20 块、块内符号交织与块间发包交织、motion/residual 分开保护及不同 MTU。更细分块通常减少单包失败的扩散，但增加头部和独立压缩开销。

GRACE 发布版本默认 entropy_encode 只估计长度，entropy_decode 未实现。本系统用实际可逆 DEFLATE 字节流补齐独立块传输；不宣称复现论文的学习熵模型码率。每个完整块的符号精确往返，不引入额外量化。质量参数 `q` 是 GRACE 残差量化步长，不能当作 H.26x 的 QP，也不能假设等码率。

## GOP 与标签

I 帧用传统 JPEG，先编码再解码得到收发共同参考；保证交付意味着零网络损失，不意味着零图像编码失真。真实 SRTP 测试中 I 帧和布局通过可靠有序 DataChannel 在启用扰动前发送并核验。这样满足本次“只扰动 P 特征”的隔离条件，但不代表线上可免费保护 I 帧；线上需计入 I 帧带宽、可靠交付时延和失败概率。

P 帧不插入 I-patch。发送端参考自己的无损特征解码结果，接收端参考自己的受损重建结果；禁止接收端借用发送端干净参考来清除误差。定期 I 帧可以重置应用误差，但网络排队状态不随 GOP 重置。

GOP 内固定丢块率适合受控标定，不能消除时序组合，也不能代替真实网络样本。固定比例但随机掩码仍有组合变化；固定掩码又会人为加入强时间相关性。本原型的 controlled_mask 模式固定同一 GOP 的丢块数和掩码，单独记录，不与逐包模式混训。正式扩展应做三类并行标签：固定率固定掩码、固定率变化掩码、真实逐包变化掩码；以后一类做最终外部验证。

第二段建议输入当前十位掩码、GOP 位置、历史丢失摘要、参考质量状态、源侧复杂度、质量档。需要更长记忆时用小型 GRU/状态空间模型。当前树模型只保留累计及上一帧丢块率，属于有限历史基线。

源复杂度除像素 SI/TI 代理外，已经提取 GRACE 量化后 motion/residual 的绝对均值、RMS 和非零比例，并单独评估反馈增强。它们需要源侧反馈及额外传输成本；这些成本目前没有计入网络仿真。SI 为亮度 Sobel 梯度统计、TI 为相邻 RGB 差分标准差，属于本原型的代理定义，不宣称严格复现某一标准复杂度指标。

## RTP 重传及帧级递交

RTP 本身不保证可靠交付，也不自动重传。[RTP](https://www.rfc-editor.org/rfc/rfc3550.html)。重传需结合反馈和发送端实现；NACK 定义见 [RFC 4585](https://www.rfc-editor.org/rfc/rfc4585.html)。

已核对的此前会话本地 Testbed fork 基线 commit 是 `8581bf4974ccb35a6cc14791caebe7fcae4a0502`，aiortc 分支报告版本 1.14.0。这一部分不是对官方 main 默认实现的描述：

- `codecs/__init__.py` 的 add_video_codec 为视频注册 nack、nack pli 及 RTX codec；包含 tokenId 系列。
- `rtcrtpreceiver.py` 视频分支建立 NackGenerator，序列缺口触发 `_send_rtcp_nack`；不能据“UDP”断言不会重传。
- `rtcrtpsender.py::_retransmit` 从 RTP history 查包；本地版本发送语句缩进在 `if self.__rtx_payload_type is not None` 内，只有存在协商 RTX payload type 才在这个路径发出。需要实际协商参数与抓包确认具体会话，静态“支持”不等于已经发生重传。
- `jitterbuffer.py` 普通视频遇序列槽缺失停止扫描；遇到下一 timestamp 才将前一组拼成 JitterFrame；默认视频 prefetch=0，但不是“marker 一到就交帧”。token 系列跳过缺槽、按 timestamp 切换递交部分数据；没有严格按实际时间的播放截止，尾帧需要显式 drain。本地 MiniCPM 另有 flush 修改，不能当作所有 codec 默认行为。
- 新的 GRACE 接收器绕过这些整帧逻辑，按明确的 frame generation time + deadline 接收完整块；不发送 NACK，不启用 RTX，也不使用自动 PLI。I 帧为独立保证交付路径。真实 SRTP 通路使用 aiortc 的 ICE、DTLS、SRTP，并通过少量私有 transport 接口接入自定义收包器，需锁版本回归验证。

首批实验关闭重传以隔离神经容错。后续应增加有期限的 NACK/RTX 对照，记录原始丢失、重传数、重传成功且及时率、最终坏块率、开销和尾时延。自动 PLI 引起额外 I 帧会改变研究条件，也需独立开关。

最终另外验证了用户指定的官方 `5G-MAG/6G-Testbed/main`，固定 commit `7231ae8e5670b67564cf28d397c2820d9403ecdc`。该分支没有捆绑上述本地 aiortc fork，使用普通 aiortc 1.14.0。普通版本的 `_retransmit` 在协商 RTX 时包装 RTX；未协商 RTX 时仍可发送历史原 RTP 包，这与本地 fork 的缩进限制不同。普通 jitter buffer 不含 token 跳缺槽分支。GRACE 新接收器在两种运行时都独立按截止时间收块，不依赖这些默认门槛，也不产生 NACK。最终官方四 profile、日志和真实 SRTP 接入已运行，源码哈希与结果另存 `official_main_sources.json`、`official_netem_*.json`，旧 fork 数据仅作诊断保留。

## 网络参数如何影响 PSNR

| 参数 | 作用链与条件 |
|---|---|
| 随机包丢失率 | 分片不全 → 整块失效 → 当前帧失真及参考漂移；受每块包数放大 |
| 截止时间 | 定义迟到是否可用，是实验协议参数；没有截止，单纯延迟不必降低离线 PSNR |
| 固定时延 | 在截止内不改变符号；超过预算使整个帧的块不可用 |
| 抖动及尾部 | 相同平均延迟仍可能有不同的超时比例；均值不足，需分位数和突发长度 |
| 带宽/帧率/每帧字节 | offered load 超过服务能力时排队增长，随后迟到或队列溢出；需报告真实字节与网络开销 |
| 队列上限 | 决定立即丢弃与迟到之间的分配；不意味着较大队列一定更好 |
| 丢失相关性 | 改变连续受损帧与块掩码；不能只用平均包丢失率预测 |
| MTU、块大小、发包顺序 | 决定分片数、损失放大及突发损失覆盖位置 |
| GOP 长度 | 影响参考漂移的积累与重置；越长越依赖历史状态 |

关键量应是“截止前完整块掩码/概率 + 参考误差状态”，网络端则需尽量估计它们。平均吞吐量、平均包丢失率、RFC RTP interarrival jitter 单独都不足以描述这个状态。当前仿真的 delay_std 和 iat_std 是统计特征，不声称等于 RFC 3550 的平滑 interarrival jitter。

## 预测与在线适配

基线包括训练均值、仅包丢失率、上游可见字节/包数、直接回归、两段回归、源反馈增强和真实块掩码 oracle。分割单位为源视频，所有质量档、GOP、随机种子和 profile 跟随视频走；验证集仅用于选择方法，最终测试应锁定。首批小样本的 video bootstrap 区间不能弥补源视频数量不足。

更强的两段模型应训练第一段的概率校准，并对 1024 种当前十位掩码求和/采样，通过应用模型传播到 PSNR 分布；历史仍需独立建模。块状态可直接从接收器无参考获得，因此第一段可用反馈在线监督，通常比对第二段做无标签适配更可靠。

PSNR 回归没有天然的分类熵目标。直接套用 [TENT](https://arxiv.org/abs/2006.10726) 的分类置信度最小熵不能证明 PSNR 预测变准。分布变化也未必只发生在输入，内容改变可能改变失真响应。建议冻结质量映射主体，监测特征与残差漂移，只更新小型校准层；用发送端低频原图/缩略图探针在接收端获得少量真实质量锚点，或用专门验证过的无参考质量代理辅助，不把代理当真实 PSNR。预顺序评估必须先预测再适配，禁止同帧标签泄漏；保存冻结模型、漂移报警、回滚和性能退化对照。当前不宣称 TTA 已产生收益。

## 实现及验收顺序

1. 固定上游提交、权重哈希及视频样本；测试十块无损往返、单包缺失整块丢弃、CRC、全帧丢失、乱序、重复和序号回绕。
2. 真实权重运行编码与独立接收解码；无扰动输出与干净基线一致；I 帧先实际传统编解码。
3. 虚拟 FIFO 敏感性试验：同源配对、逐包记录、区分随机丢失/溢出/迟到，生成足够的帧级标签。
4. 原 Testbed netemu 在独立 Linux namespace 中作用于真实 SRTP 包；核对抓包、tc 计数与接收掩码并清理 namespace。短真实试验与大批虚拟仿真分别报告。
5. 按视频分割训练预测器，报告直接/两段/反馈/oracle 对照及失败案例。
6. 扩大分辨率、场景、GOP 和质量档，增加独立日期及未见网络条件；再开展有期限重传、可见扩展及预顺序在线适配。
